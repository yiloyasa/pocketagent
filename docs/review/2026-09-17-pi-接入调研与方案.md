# PocketAgent 接入 Pi:调研与方案

> 日期:2026-09-17 基准:PocketAgent(Android 38 个 Kotlin 文件约 11.3k 行 + Go daemon + proto/v1)
> 调研对象:本机 `@earendil-works/pi-coding-agent` **0.85.1**
> 方法:通读该版本随包文档(rpc / session-format / sessions / security / settings / providers / json / windows / termux / keybindings),
> 实测本机运行环境与 Pi 配置目录,并逐文件核对 PocketAgent 现有 Provider、连接层、会话层、终端实现。
> **诚实前提**:RPC 的行为描述来自这个版本的随包文档与协议定义,**尚未启动真实进程验证**。
> 因此 §11 的 P0 探针是开工第一步 —— 本文所有"能接"的结论都应先用探针变成"本机可复现"。

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 接入方式 | 走 `pi --mode rpc`,由 daemon 起子进程、做协议转换。**不要**用 `--mode json`(一次性)或 `--print`(非交互),也不要在手机上渲染 TUI |
| 难点在哪 | 不在协议,在四件事:**手机键盘打不出终端键**、**工作目录一旦选定不可中途更换**、**轮次必须与手机连接解耦且支持游标续传**、**断网时手机端本来什么都没有** |
| 最大结构性收益 | Pi 会话文件是**唯一真相**且带**可持久游标**(`get_entries(since=...)`),顺手修掉现有"跨轮工具历史不落库"的技术债,并让断点续传有正解 |
| 最大风险 | Pi **无沙箱**(官方明说),且审批要靠扩展自己拦;扩展弹窗无超时会**永久挂起**整轮 |
| 建议路径 | 先 P0 探针 → P1 Provider 打通 → P2 交互(键栏/命令面板) → P3 多 agent 会话 → P4 可靠性与离线 |

## 1. 为什么是 RPC,不是别的

Pi 同时提供四条外部接口,逐条判定:

| 接口 | 形态 | 判定 |
|---|---|---|
| `pi --mode rpc` | stdin/stdout 双向 JSONL,长驻进程 | **选它**。命令+事件双向、支持审批子协议、支持会话切换 |
| `pi --mode json "prompt"` | 一次性,输出事件流 | 只适合冒烟,不能多轮、不能审批、不能中断 |
| `pi -p`(print) | 单次问答 | 同上,更弱 |
| `@earendil-works/pi-coding-agent` SDK(Node 内嵌 `AgentSession`) | 库里直接调 | 需要把 daemon 的会话逻辑重写成 Node 服务,**与现有 Go 架构冲突**,不选。但它是很好的"协议语义参考实现" |

选 RPC 的关键理由有三条,都直接对应本项目已踩过的坑:

1. **双向**:手机上"取消/补充/审批"都要能回传。`-p` 和 `--mode json` 都是单向管道。
2. **长驻**:一次 `pi` 进程承载多轮对话,省掉每轮冷启动(现有 codex 桥接也是这个思路)。
3. **有审批子协议**:`extension_ui_request/response`,能接进现有审批卡。

代价:需要 daemon 管子进程生命周期、处理 stdout 分帧、处理版本漂移。这些 `codexapp/client.go` 已经有一整套可复用。

## 2. 本机环境实测(接入的前置条件)

| 项 | 实测值 | 影响 |
|---|---|---|
| Pi 版本 | 0.85.1,入口 `dist/bundle/cli.js` | 协议随版本变,需固定版本 + 启动握手校验 |
| 启动方式 | 现在靠 `pi.ps1` 垫片(内部再调 node) | **daemon 应直接 `node .../dist/bundle/cli.js`,不要经过 .ps1**,省一层 shell,也避免 PowerShell 策略干扰 |
| Node | v26.3.0(`C:\Users\yanzi\AppData\Local\Programs\nodejs\node.exe`),要求 >= 22.19.0 | 满足。但要显式定位,**不能依赖 PATH**(见下) |
| Git Bash | `C:\Program Files\Git\bin\bash.exe` 存在 | Pi 在 Windows 默认用它跑 `bash` 工具,所以这条链是通的 |
| 配置目录 | `~/.pi/agent/` 已存在 | 见下 |
| 已登录 provider | `auth.json` 中为 `zai-coding-cn` | 手机端模型列表应与 Pi 实际可用模型对齐,而非硬编码 |
| 全局设置 | `settings.json` 装了 4 个包:`pi-web-access`、`pi-subagents`、`pi-hermes-memory`、`pi-lens` | **这些扩展在 RPC 模式下同样加载**,必须处理它们的 UI 请求(§4.6) |
| 会话目录 | 4 个工作区、10 个 `.jsonl` | 见 §6.1 |
| 工作区命名 | `--C--dev-pocketagent-daemon--`、`--C--Users-yanzi--`、`--G--试验区--`、`--G--项目1--` | **反推路径不可靠**,且证明**中文路径可用** |

后两点很关键,展开说:

- **中文路径可用是实测结论**,不是推测。`G:\项目1` 已经产生了会话目录 `--G--项目1--`。所以不必像 Android 构建那样再做 ASCII 镜像。
- **目录名不可反推**:`/` 换成 `-` 是有损的(盘符的 `:` 也变成了 `-`,路径里的 `-` 与分隔符同形,大小写也不保留)。所以"列出某工作区的 Pi 会话"必须**读文件头部的 `cwd` 字段**,不能解析目录名。这一个细节写错,会话就会串到别的工作区去。

另一个必须提前确认的点:**daemon 目前由计划任务经 WMI 派生**(见根 README 的看门狗链路)。WMI 派生的进程环境变量未必等于用户交互登录时的环境。codex 能跑通说明基本可用,但 Pi 多了两个额外依赖 —— `~/.pi/agent` 的定位(依赖 `USERPROFILE`/`HOME`)和 node 的定位(依赖 `PATH`)。**P0 探针里必须包含"从 daemon 的真实启动环境里拉起 pi"这一项**,否则会出现"我在终端里跑得好好的,手机上一发就报找不到凭据"。

## 3. 协议映射:Pi 事件 → 现有 pb 消息

现有 `TurnServerMessage` 的 oneof 已经够用,多数是直译:

| Pi(RPC) | PocketAgent | 备注 |
|---|---|---|
| `message_update` → `text_delta` | `TextDelta` | 直译 |
| `message_update` → `thinking_delta` | `ThinkingDelta` | 直译 |
| `message_update` → `toolcall_start/delta/end` | `ToolCallUpdate(STARTED)` | 参数要自己按 `contentIndex` 拼 |
| `tool_execution_start/update/end` | `ToolCallUpdate` | **需要新增 UPDATE 相位**,见下 |
| `extension_ui_request(confirm/select)` | `ApprovalRequest` | 这是审批入口,不是 `tool_execution_start` |
| `get_session_stats.contextUsage` | `UsageUpdate` + 现有用量环 | 直接给百分比,不用自己算 |
| `compaction_start/end` | 建议复用/新增状态事件 | 手机要显示"正在压缩上下文" |
| `auto_retry_start/end` | 建议对应 `CodexEvent` 风格的通用状态事件 | 现在没有通用位 |
| `agent_settled` | `TurnCompleted` 的判定依据 | **不能只看 `agent_end`** |

### 3.1 必须改的协议点

1. **`ToolCallUpdate` 缺 UPDATE 相位**。proto 里只有 `STARTED/FINISHED`,而 Pi 的 `tool_execution_update` 会持续吐进度(长命令输出)。语义上是"同一 callId 的进行中"。建议加 `UPDATE` 相位,或明确"重复发 STARTED + 同 callId"的约定并让 App 端按 callId 覆盖。
2. **通用状态事件缺失**。现有 `CodexEvent` 名字就绑死了 Codex。Pi 的重试、压缩、限流、扩展报错都没地方放。建议抽一个与供应商无关的 `AgentEvent`(或把 `CodexEvent` 改名),否则接第三个 agent 时又要抄一遍。
3. **`ErrorInfoCarrier` 复用**。Pi 的错误会以 `success:false` 的 response 或事件形式出现,需要一个统一的"结构化错误"出口,接口已经存在,直接实现。

### 3.2 协议细节坑(逐条都有后果)

| # | 事实 | 后果 / 必须怎么做 |
|---|---|---|
| 1 | 分帧**只按 `\n`**,且官方明确 Node 的 `readline` 不合规(会把 U+2028/U+2029 当换行) | Go 的 `bufio.Scanner` 默认只切 `\n`,是合规的;但**默认 64KB token 上限会炸**。`codexapp/client.go` 已用 4MB `bufio.ReaderSize` —— Pi 要更大,因为**图片走 base64 进单行 JSON**,一张手机照片的 base64 就有数 MB |
| 2 | stdout 只放协议,日志走 stderr | daemon 必须分开抓;不要把 stderr 混进 JSONL 解析 |
| 3 | 流式中发 `prompt` **必须**带 `streamingBehavior`,否则直接返回错误 | 正好对应现有"中途补充"(`TurnSupplement`)→ 映射成 `steer`;想排队等结束 → `followUp` |
| 4 | `success:true` 只表示**已受理**,后续失败走事件流 | 不能把 response 当轮次结束 |
| 5 | `agent_end` 之后仍可能有重试/压缩/排队续跑,**`agent_settled` 才是真结束** | 否则手机会提前停转圈 |
| 6 | `get_entries(since=entryId)` 是**持久游标**(跨客户端重启有效),且包含压缩前历史与废弃分支 | 这是断线续传的正解,见 §8.2 |
| 7 | `message_update` 只给**增量**;`tool_execution_update.partialResult` 给的是**累积值** | 两者语义相反,极易写错:文本要拼,工具输出要直接替换 |
| 8 | `prompt.images` 用 base64,mimeType 必填 | 与现有附件链路能对上,但要注意单行体积 |
| 9 | `bash` 命令与 `bash` **工具**不是一回事 | `bash` 命令是"直接执行并把输出塞进上下文(下一轮 prompt 才进 LLM)";别和工具调用混在同一张卡里 |

## 4. 把"终端 agent"做得顺滑

Pi 的原生形态是 TUI(整屏、方向键、斜杠命令、树状会话)。**手机上不要复刻 TUI**。理由:屏幕只有 6 寸、没有真键盘、ANSI 全屏重绘在移动端是灾难。

正确做法是**把终端语义翻译成结构化界面**:

### 4.1 聊天页承担 Pi 的"主输出"

- 文本/思考/工具三段,直接用现有气泡与工具卡体系。
- **工具卡是 Pi 的主战场**(它是个 coding agent,一轮里大半是读文件、改文件、跑命令)。要求:
  - 命令/文件路径用等宽字体,长行横向滚动而不是折行(折行会让 diff 和输出彻底读不了);
  - 输出默认折叠到 N 行,可展开;**流式期间用 `partialResult` 原地替换**,不要每来一块就追加一块(否则一屏全是重复内容);
  - 失败的调用(`isError:true`)要红标,不要和成功混在一起;
  - 一键复制命令、一键复制输出。
- **改文件的 diff 要单独渲染**,不要当普通文本。Pi 的 `edit`/`write` 工具结果在 `details` 里带结构化信息,值得单独取出来做 diff 视图(现有 `GitScreen` 已有 diff 渲染可复用)。

### 4.2 真终端(现有 xterm)怎么与 Pi 分工

现在 `TerminalScreen` 是"电脑上的真 PTY",这是**独立价值**,保留。分工说清楚:

| 场景 | 用哪个 |
|---|---|
| 让 Pi 干活、看它思考与动手 | 聊天页(结构化) |
| 我自己要敲命令、看交互式程序(vim/top) | 真终端(xterm + PTY) |
| 看 Pi 跑过的命令的完整输出 | 聊天页工具卡展开 |
| 需要和 Pi 同步目录 | 终端页切目录时同步聊天页创建会话的工作区 |

**不要**试图把 Pi 的 TUI 塞进 xterm 来"复用终端页"——那等于放弃结构化事件,还要在手机上解决全屏重绘和键位问题。

### 4.3 长任务的可观测性(这是"顺滑"的核心)

一个 coding agent 一轮可能跑几分钟到几十分钟。手机端必须随时能回答"它现在在干嘛、卡没卡":

- 当前工具名 + 已跑时长 + 最近一行输出(折叠态也能看见);
- 上下文用量百分比(取 `get_session_stats.contextUsage`,直接可用);
- 压缩中 / 重试中(`compaction_*`、`auto_retry_*`)要有明确状态,否则用户会把"压缩上下文时的静默"当成卡死;
- 排队中(steer/followUp 队列,`queue_update` 给的是完整队列)要显示 pending 条数;
- 计划步骤(现有 `CodexEvent.plan_steps` 那套 UI)Pi 侧暂时没有对应物,不要假装有。

### 4.4 模型与思考强度

`get_available_models` / `set_model` / `get_available_thinking_levels` / `set_thinking_level` 与现有"模型·强度"胶囊一一对应。注意:

- 手机端模型列表**必须以 Pi 实际返回为准**(本机只登录了 `zai-coding-cn`,别把模型写死);
- 每轮覆盖(`TurnInput.model_id`/`effort`)与 daemon 侧 `set_model` 的关系要定清楚:建议**会话级持久 + 轮次级覆盖**,与现有 codex 的处理一致。

### 4.5 斜杠命令:把"敲"变成"点"

`get_commands` 会返回可用命令(含扩展命令与技能)。手机上是**命令面板**(底部抽屉,可搜索),不是让用户手打 `/`。至少覆盖:`/compact`、`/name`、`/model`、`/new`、`/resume`。

### 4.6 扩展弹窗:必须防挂死

本机装了 4 个扩展包,**它们在 RPC 模式下同样加载**。它们可以随时弹 `extension_ui_request`:

- 有 `timeout` 的会自动兜底;
- **没有 `timeout` 的会永久等待**,整轮就此挂住,手机上表现为"一直转圈";

所以 daemon 侧对每个 `extension_ui_request` 都要:转发给手机(能对应到审批卡就转审批,`select` 可以转成多选卡)、**加自己的超时**,超时或手机断开时回 `cancelled: true`(失败安全,不要默认放行)。这条与现有 `approve()` 里 `readerDone` 的处理是同一类问题,可以直接沿用那个模式。

## 5. 手机键盘 ≠ 电脑键盘

这是这次调研里最容易低估、实际上最影响"顺手程度"的一块。分两个界面谈。

### 5.1 聊天输入区(现状问题)

现在(`ChatScreen.kt` 约 1664-1740 行)是:`BasicTextField`,`maxLines=4`,并且 **`enabled = !st.running`** —— 一轮在跑的时候输入框是禁用的。

对 terminal agent 这是硬伤:Pi 一轮十分钟很正常,用户中途想补充方向(`steer`)、想追加要求(`followUp`)都被挡住,只能等它跑完。**必须改**:

| 改动 | 理由 |
|---|---|
| 运行中**可输入**,发送按钮变成"补充(steer)"语义,长按可选"排队(followUp)" | 协议本来就支持,不用白不用 |
| 保留"停止"按钮走 `abort` | 已有取消链路 |
| 输入框高度与 IME 行为:Enter 换行、发送靠按钮 | 手机上"Enter 即发送"极易误触,长 prompt 尤其 |
| 保留 `imePadding()` | 已做对,不要动 |
| 语音输入 | 手机上打字成本最高的场景,后置但也别忘 |

### 5.2 真终端的虚拟键栏(目前**完全没有**)

现状:`terminal.html` 已经处理了**物理键盘**的 `keydown`(`Tab`→`\t`、`Shift+Tab`→`ESC[Z`、`Esc`→`\x1b`),这段写得对。但是:

> **没有任何软键盘辅助键栏。软键盘上打不出 Ctrl、Esc、Tab、方向键。**

后果:手机上 vim 出不来、less 退不出、`Ctrl+C` 停不掉、`Tab` 补全没有 —— 真终端在手机端只有一半可用。

**方案:在终端上方加一行可横向滚动的辅助键栏,用"粘滞修饰键"设计。**

键位建议(按使用频率):

| 区 | 键 |
|---|---|
| 修饰(粘滞) | `Ctrl`、`Alt` |
| 控制 | `Esc`、`Tab`、`Shift+Tab` |
| 方向 | `←` `↑` `↓` `→`、`Home`、`End`、`PgUp`、`PgDn` |
| 高频组合 | `Ctrl+C`、`Ctrl+D`、`Ctrl+Z`、`Ctrl+L`、`Ctrl+R` |
| 符号 | `/` `-` `|` `~` `*` `$` |
| 操作 | `Enter`、粘贴、收起键盘 |

交互细节(这些决定好不好用):

- **粘滞语义**:点 `Ctrl` 高亮,下一次按键带上修饰后**自动复位**;**连点两次锁定**(长按也可以),再点一次解锁 —— 和 Termux 的用法一致,用户已有心智模型。
- 高亮必须显眼,锁定与临时两种状态要能分辨。
- 键按下要有触感/视觉反馈(现有 `PaAnim` 有一整套动效语言,保持一致)。
- 键栏**不要吃掉终端高度**:它应随软键盘一起升起(`imePadding`),收起键盘时隐藏或收成一条细线。
- 发送的是**真实字节序列**(`\x03`、`\x1b`、`\x1b[A`…),不是键名 —— 复用现有 `TerminalBridge.sendInput` 通道即可,不用改协议。

### 5.3 输入法(IME)相关的具体坑

| 坑 | 处理 |
|---|---|
| 软键盘 Enter 发的是 `\r` | 对 shell 正好,不用改 |
| 退格:部分 IME 发 `\b`(0x08),xterm 期望 `\x7f` | 在 `terminal.html` 的 `keydown` 里统一映射 |
| 中文输入法组合期会连发中间态 | 只在 `compositionend` 后才把文本发给 PTY,组合中不上屏到远端 |
| 长粘贴被逐字符发送 | 一次 `onData` 批量发(现在 `term.onData` 已经是整体回调,别在外面按字符拆) |
| 大粘贴触发 readline 重排 | 现有 `disablePasteBurst` 类行为在 Pi 侧也有对应考量,注意节奏 |
| 输入法遮挡终端 | `visualViewport` 监听**已经做了**(`fitAndReport`),复用即可 |

### 5.4 用"点"替代"敲"的另外两处

- **审批卡**:危险操作尽量做成按钮(允许一次/总是允许/拒绝),不要要求输入 y/n。
- **工具卡**:复制、重跑、展开输出,都是点按,不是按键。

## 6. 会话管理与工作目录

### 6.1 Pi 会话怎么被我们发现

事实(实测):

```
~/.pi/agent/sessions/--<工作目录变形>--/<时间戳>_<uuid>.jsonl
```

- 文件是 JSONL;**第一行是 header**,含 `type/version/id/timestamp/cwd`(有父会话时还有 `parentSession`);
- 之后是按 `id`/`parentId` 组织的**树**(v3);
- 会话名来自 `sessionName`(用 `set_session_name` 设置,或启动时 `--name`);
- 删除会话 = 删 `.jsonl`(官方文档也这么说,且交互模式下会优先用 `trash` 命令走回收站)。

**实现要点:**

1. 遍历 `sessions/*/*.jsonl`,**读 header 的 `cwd` 判断归属**,不要解析目录名(见 §2)。
2. 标题优先级:`sessionName` → 首条 user 消息摘要 → 时间戳。
3. 目录 mtime/文件 mtime 用于排序,不要用目录名里的路径。
4. 单文件可能很大(见过的有 22KB,长期会话会到 MB 级)。**列表页只读 header + 前几行**,不要为了列表把整个文件解析一遍。

### 6.2 工作目录:必须先定,且不能中途换

**这是接入 Pi 最容易被忽略的硬约束。**

Pi 的会话**绑定创建时的工作目录**(session 的 `cwd`,以及它决定会话文件落在哪个目录下)。现有 PocketAgent 的 `CreateThread` 允许传 `workspace`,而终端页还能随时切目录。对 Pi 会话,规则必须更严:

- 工作目录在**创建会话时选定**,之后**只读**;
- 想换目录 = **新建会话**(UI 上明确写出来,不要让用户以为能改);
- 现有 `FolderPicker`(走 gRPC `ListDirectory`)直接复用,`AgentConnection.addRecentWorkspace` 已经记最近目录;
- 创建 Pi 会话时,daemon 用该目录作为子进程的 `cwd` 启动 pi;
- 建议同时给 Pi 传 `--session-dir`,把会话文件收到 PocketAgent 自己的数据目录下,**避免和用户手敲的 pi 会话混在一个池子里**(也可选不隔离,取决于是否想双向看到对方的会话 —— 这是个产品决策,不是技术限制)。

### 6.3 我们的 Thread 与 Pi session 怎么映射

建议 **1:1**,并且**让 Pi 的会话文件成为内容的唯一真相**:

| 我们的字段 | 来源 |
|---|---|
| `Thread.ModelID` | `pi/<provider>/<model>`,与现有 `codex/...` 风格一致 |
| 新增 `AgentID = "pi"` | 会话归属,见 §7 |
| 新增 `ExternalSessionRef` | `{SessionID, SessionFile, Cwd}` |
| 历史消息 | **按需向 Pi 要**(`get_messages` / `get_entries`),而不是自己当真相 |

好处很直接:顺手解决现有的两条技术债 —— "跨轮对话的工具调用历史未持久化"和"daemon 重启后要 resume 否则静默丢消息"。Pi 这边只要重新 `switch_session` 到同一个 session 文件,历史天然完整。

保留现有 `codex_thread_id` 字段不动(兼容老数据),新字段用通用的。

### 6.4 删除 / 重命名 / 归档

- **重命名**:走 `set_session_name`,让电脑端 `pi -r` 也能看到同一个名字(双端一致,和现在 codex 标题同步的做法一致)。
- **删除**:删 `.jsonl`。用回收站语义(或先移到一个 `.trash` 子目录),避免误删不可逆。
- **归档**:Pi 没有归档概念。我们的"归档"只作用于自己的列表,不要假装同步 —— **归档一个 Pi 会话后,电脑上它依然在**,UI 文案要说清楚。
- 删除 Pi 会话时**必须连带清掉**本地快照(§9),否则"删了还能看见"。

### 6.5 分支树怎么处理

Pi 的会话是**树**(可在任意历史点继续,产生分支),PocketAgent 现在是**线性列表**。第一版:

- 只呈现**当前活跃分支**(`get_messages` 给的就是活跃路径的线性视图),这与现有 UI 完全兼容;
- 增量同步用 `get_entries(since=...)` 拿**追加序**的条目(它包含压缩前历史与废弃分支,适合做"完整审计视图",但**不要**直接拿它渲染主对话,否则用户会看到不存在的分支);
- `/tree`、`/fork`、`/clone` 的图形化**后置**。手机屏幕上做树状导航的收益远小于成本,先用命令面板兜住(见 §4.5)。

## 7. 怎么在 PocketAgent 里显示不同 agent 的会话

### 7.1 现状与问题

- `store.Thread` 只有 `CodexThreadID` 一个外部会话字段,是**为 Codex 定制的**;
- 会话列表只有"我们的会话"一源,"电脑上已有的会话"是 Codex 专属的一条导入路径(`ListCodexThreads` / `ImportCodexThread`);
- 首页 Agent 网格里 `pi` 是**硬编码的"开发中"**(`HomeScreen.kt` 约 152 行),`SettingsScreen` 里有 agent 名与图标映射;
- **隐患**:`providerFor()` 找不到对应 provider 时会**回退到默认 provider**。多 agent 之后,这会导致"我明明选了 Pi,结果发给 Codex 了"。这个必须改成显式失败或明确降级提示。

### 7.2 建议的数据模型

```
Thread
  ├─ AgentID            "codex" | "pi" | ...        ← 新增,归属
  ├─ ExternalSessionRef  {SessionID, SessionFile, Cwd}  ← 新增,通用
  └─ CodexThreadID      保留,兼容老库
```

`proto` 侧相应加通用字段(如 `external_session_id`、`external_session_file`、`agent_id`),并保留 `codex_thread_id` 兼容。**改 proto 记得两处同步**(`proto/v1/` 与 `android/app/src/main/proto/v1/`),这是已知流程。

### 7.3 呈现方式:两源 + 归属徽标

保持现有的"两源"心智,不要混成一条:

| 源 | 内容 | 获取方式 |
|---|---|---|
| 活跃会话 | 我们自己库里的 thread(已经和某个 agent 绑定) | 现有 `ListThreads` |
| 电脑上的会话 | 各 agent 的原生历史 | Codex 已有 app-server 列表;Pi 是**读本地文件**(便宜、快、离线也能读) |

UI 上的三条规则:

1. **每条会话行必须带 agent 徽标**(图标资源已存在:`agent_pi`、`agent_codex`),否则用户分不清这条是哪个 agent 的上下文;
2. 顶部加**筛选 chips**(全部 / Codex / Pi / …),默认"全部";
3. **导入流程复用现有交互**:Pi 那条比 Codex 更简单(本地文件直接读,不需要 app-server 往返)。

另外,Pi 会话有个 Codex 没有的特性值得利用:**电脑上的 Pi 会话本身就带工作目录**,所以可以按工作区分组显示 —— 这和用户"我想继续昨天在某个项目里的活"的心智完全吻合。

## 8. 连接可靠性

### 8.1 已经做扎实的部分,直接复用

现有连接层是产品级的(见 2026-09-16 缓存与离线审查 §3.1):

- 多候选回退:`lastGoodAddr → USB → 局域网 → Tailscale → 手填`;
- 断线后指数退避重连 + `NetworkCallback` 网络事件即时唤醒;
- `connectionEpoch` 驱动全局刷新;
- `TurnKeepAliveService` 前台服务保活;
- **轮次与连接解耦**:`StartTurn` 里 `runCtx` 用的是 `context.Background()` 而不是流上下文 —— 手机断了,电脑上继续跑,结果照样落库。

这些**一行都不用改**,Pi 的 daemon 侧照搬。

### 8.2 必须新增:事件缓冲 + 游标续传

现有恢复方式是"重连后**重新拉全量历史**"(`resyncFromDaemon` 轮询)。这对 Pi 不够好,原因:Pi 一轮里事件量很大(逐字文本、工具进度),断线 30 秒再全量重拉,既慢又丢过程感。

Pi 恰好给了正解 —— `get_entries` 的 `since` 是**跨重启有效的持久游标**。设计:

```
daemon 侧每线程:
  ringBuffer(最近 N 条事件, 每条带单调 seq)
  lastEntryId          ← 最近一次从 Pi 拿到的条目 id

手机重连:
  带上 lastSeq
    → 缓冲里有:从缓冲重放(满速、瞬时)
    → 缓冲不够:用 get_entries(since=lastEntryId) 向 Pi 要权威增量
    → 再不行:get_messages 全量兜底
```

这一层做好了,"断开再回来"的体验从"等它重新加载"变成"立刻接上,像没断过"。

### 8.3 daemon 重启后怎么重挂载

Pi 子进程会随 daemon 一起死(看门狗把 daemon 拉起来时,子进程是新的)。**这里有现成的教训可以抄**:codex 那边用 `gen` 计数标记子进程代号,重启后**必须先 `resume`**,否则请求打到子进程不认识的 threadId 会被静默吞掉 —— 实测表现为"无报错、无事件、永远转圈"。

Pi 侧同样处理:每次(重)起子进程后,对已有会话**先 `switch_session(sessionFile)`**,确认 `get_state` 返回的 `sessionFile` 与预期一致,再允许发 prompt。**这个握手不能省。**

### 8.4 失败模式与应对

| 失败 | 表现 | 应对 |
|---|---|---|
| 手机断网/拔线 | 流断 | 轮次继续;缓冲留住事件;重连按 §8.2 续传 |
| daemon 重启 | 子进程全死 | 按 §8.3 重挂载;store 里的 `ExternalSessionRef` 是重挂载的依据 |
| Pi 子进程崩溃 | 流结束、无收尾帧 | 检测子进程退出 → 主动发 `TurnFailed` 并置会话为 IDLE,**不要让手机继续转圈** |
| Pi 卡住(扩展弹窗/网络挂起) | 长时间无事件 | 心跳:daemon 定期 `get_state`(它含 `isStreaming`);同时给每个扩展请求设超时(§4.6) |
| 模型 429 / 网络抖动 | 重试中 | 转发 `auto_retry_*`,转圈不能停,要显示"重试中(第 N 次)" |
| 上下文压缩 | 静默、耗时长 | 转发 `compaction_*`,显示状态 |
| 手机关屏 | 前台服务被杀 | 已有 `TurnKeepAliveService`;Pi 轮次因为跑在 daemon 上,本来就不受影响 |

### 8.5 连接层还需要补的两点

1. **心跳/健康探针升级**:现在 `paguard` 只做 TCP 端口探测。gRPC 侧建议加一个轻量 `HostInfo`/`ping`,能在"端口开着但服务半死"时也发现问题。
2. **失败原因要能显示出来**:现有 `ConnectionDiagnostics` 已有基础,Pi 接入后新增的失败源(找不到 node、找不到 `~/.pi/agent`、没登录 provider、版本不匹配)都要落成**用户看得懂的文案**,而不是 "连接失败"。

## 9. 断网可见

### 9.1 现状(引用 2026-09-16 审查)

- **不存在内容缓存**:`listThreads` / `getThreadHistory` 全部直连 daemon;
- 断网打开 app:会话列表**空白**、进会话报错"无法加载会话历史";
- 已经能离线的只有:已下载文件、任务中心、设置/置顶/用量回显。

### 9.2 Pi 场景下"离线可见"能做到什么

先把边界说清楚,避免做出做不到的承诺:

- **Pi 的会话真相在电脑上**,手机端不可能离线"继续干活" —— PC 不在线就没有执行环境;
- 能做的是**只读可见**:看过什么,断网时还能看什么。

### 9.3 三档方案(按投入排序)

| 档 | 内容 | 成本 | 依据 |
|---|---|---|---|
| **L1 列表 + 最近消息快照** | 每次成功加载后,把 `(id, title, agentId, updatedAt)` 与每会话最近 N 条写本地;断线时渲染快照并标"离线快照 · X 日前的记录",输入框置灰 | 低 | 对应审查里的 C3 / O1 / O2,是现成结论 |
| **L2 会话导出 HTML 落手机** | 用 Pi 的 `export_html` 生成自包含 HTML,经现有下载链路落到手机,用**已有的** `BrowserScreen` 打开 | 中,但**大部分代码已存在** | `export_html` 是 Pi 原生能力;下载与浏览器是本项目已有能力 |
| **L3 离线排队发送** | 发不出去的消息落本地队列,重连后按序发出 | 中 | 与 `steer/followUp` 语义要注意不要打架 |

**L2 是这次调研里性价比较高的一条**:给一个 Pi 会话点"导出到手机",就得到一个完整、可离线翻看的会话存档,而且不需要新建渲染管道。

### 9.4 明确不做

- 离线改文件、离线跑命令、离线审批 —— **不可能**,因为没有执行环境。UI 上要明确"需要连接",不要让用户对着置灰的按钮猜。
- 离线状态的**主动告知**:各 gRPC 依赖页统一消费 `connState`,down 时整页置灰 + 常驻顶条"已与电脑断开,正在自动重连…",替代现在分散的一次性报错文案(审查 O5 已有此建议)。

## 10. 安全与信任边界

| 事项 | 事实 | 我们的处理 |
|---|---|---|
| Pi 无沙箱 | 官方 `security.md` 明确写:以启动它的用户权限运行,**不含任何沙箱**,项目信任只管"是否加载项目资源",不是安全边界 | 必须在 UI 上说清楚:Pi 会话 = 电脑上的完整权限。审批卡不是"沙箱",是"提醒" |
| 审批从哪来 | Pi **没有内建审批**。要靠扩展在 `tool_call` 钩子里拦,再弹 `confirm` | daemon 启动时注入我们的审批扩展;**默认拒绝**,超时/断线一律 `cancelled` |
| 凭据 | `~/.pi/agent/auth.json` 存订阅/API 凭据,token 会自动刷新 | 子进程继承环境;**不要把 auth.json 内容经手机端传输**。手机端也要能显示"Pi 已登录/未登录",但只显示状态,不显示凭据 |
| 项目级资源 | 非交互模式下 `defaultProjectTrust: "ask"` 等于**忽略**项目资源;要加载需 `always` 或 `--approve` | 这是个**产品决策**:若不显式信任,用户会发现"项目里的 AGENTS.md/skills 没生效"。建议在会话创建时让用户明确选"信任本项目" |
| 手机端现状 | token 明文存 SP + gRPC 明文(`usePlaintext`) | 已有债(审查 S3/S5)。**接 Pi 之后这条债更重要了** —— 远程能触发 PC 上的任意命令,链路被窃听的后果升级。建议与 Pi 接入同期或紧随其后做 TLS + EncryptedSharedPreferences |
| 危险命令 | Pi 的 bash 工具能跑任何命令 | 扩展里做规则拦截(如 `rm -rf`、`git push --force`、写系统目录),命中则强制审批 |

## 13. 一句话总结

**协议层不难 —— Pi 的 RPC 事件与现有 `TurnServerMessage` 几乎能直译,`codexapp/client.go` 的进程管理也能直接复用。
真正决定成败的是四件工程活:把终端键位变成可点的控件、把工作目录约束讲清楚、用 `get_entries` 游标把断线续传做成"像没断过"、以及在手机端补上现在完全没有的离线只读快照。
另外两件事不能含糊:Pi 没有沙箱(所以审批和链路加密的分量比现在更重),以及文档与真实进程之间还差一个 P0 探针。**
