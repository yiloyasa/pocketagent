# 为什么改了这么多 bug，APK 还是只有二十几 MB

> 日期：2026-09-17
> 基准：PocketAgent（Android Kotlin/Compose + PC Go daemon）
> 触发问题：「改动这么多 bug，apk 仍只有二十几 MB 的原因（改动在哪里，是 daemon 还是其他不可见部分）」

---

## 0. 一句话结论

**因为 APK 里根本没有 daemon。** 本轮改动的大头（Go 侧 17,771 行）编译成的是**电脑上**的
`pocketagentd.exe`（19.5 MB），跟手机安装包完全无关；而手机侧那 19,514 行 Kotlin，
编译成 DEX 只占 **1.13 MB**（8.5%）。

APK 的体积从来不是由"改了多少 bug"决定的，而是由**依赖了哪些框架**决定的。

顺带查出一个真问题并已修复：一个**全项目零引用**的依赖占了 DEX 的一半。
删掉后 APK **20.0 MB → 12.41 MB（-7.6 MB，-38%）**。

---

## 1. 改动落在哪里：四层结构

| 层 | 位置 | 规模 | 是否进 APK |
|---|---|---|---|
| **手机 App** | `android/app/src/main/java/**` | 44 文件 / 19,514 行 Kotlin | ✅ 是（DEX 1.13 MB） |
| **PC daemon** | `daemon/**` | 53 文件 / 17,771 行 Go | ❌ **否**，是电脑上的 `pocketagentd.exe`（19.5 MB） |
| **契约** | `proto/v1/*.proto` | 7 个文件 | ⚠️ 只把生成的桩类打进包（467 KB） |
| **网页资源** | `android/app/src/main/assets/**` | terminal.html + xterm.js | ✅ 是（0.09 MB） |

关键点：**手机只是个遥控器**。agent 循环、codex 桥接、终端 PTY、文件系统、Git——
全都在电脑那个 Go 进程里。所以"daemon 改了一堆东西"在 APK 上不会体现，
只会体现为电脑上那个 exe 变了。

---

## 2. APK 里到底装了什么（实测）

干净重建（`clean assembleDebug`）后的实测构成，APK 共 **12.41 MB**：

| 分类 | 压缩后 | 占比 |
|---|---|---|
| DEX（Kotlin/Java 编译产物） | 11.50 MB | 93.2% |
| `resources.arsc` 资源索引表 | 0.41 MB | 3.3% |
| `res/` 资源（图标/字体/XML） | 0.27 MB | 2.2% |
| `assets/` 网页资源 | 0.09 MB | 0.7% |
| `lib/` 原生库 | 0.04 MB | 0.3% |
| 其他 + 签名 | 0.03 MB | 0.3% |

**93% 是 DEX**。继续拆 DEX 内部（`apkanalyzer dex packages`，未压缩口径，合计 12.7 MB）：

| 包 | 大小 | 占比 | 是谁 |
|---|---|---|---|
| `androidx.compose.*` | 5.94 MB | 44.5% | Compose UI 框架本身 |
| ├ `androidx.compose.ui` | 1.70 MB | 12.7% | |
| ├ `androidx.compose.material3` | 1.60 MB | 12.0% | |
| └ `androidx.compose.foundation` | 1.52 MB | 11.4% | |
| `com.google.*`（Guava） | 1.76 MB | 13.2% | gRPC/Guava 依赖 |
| **`dev.pocketagent.app.*`** | **1.13 MB** | **8.5%** | **我们自己的 App 代码（全部 19,514 行）** |
| `kotlin` stdlib | 0.96 MB | 7.2% | |
| `kotlinx`（协程） | 0.61 MB | 4.6% | |
| `io.grpc` | 0.58 MB | 4.3% | |
| `pocketagent.v1` | 0.47 MB | 3.5% | proto 生成的桩类 |

**我们自己的代码只占 8.5%。** 剩下 91.5% 是框架与依赖——改 bug 改的是这一小块的**逻辑**，
不改框架，所以对体积几乎没有影响。

一个直观的换算：19,514 行 Kotlin ≈ 1.13 MB DEX，**平均每行约 58 字节**。
就算本轮改了 3,000 行，DEX 也只动 ±180 KB，相当于 APK 的 1.4%。

---

## 3. 顺带查出的真问题：一个没人用的依赖占了一半 DEX

排查过程中发现 `android/app/build.gradle.kts` 里有：

```kotlin
implementation("androidx.compose.material:material-icons-extended")
```

而全项目对 `Icons.*` 的引用数是 **0** —— 所有图标都用 lucide 矢量图
（`res/drawable/ic_lucide_*.xml`，53 个）。

它带来的代价（`apkanalyzer` 实测，未压缩 DEX）：

| 包 | 大小 |
|---|---|
| `androidx.compose.material.icons` | **14.20 MB** |
| └ `...icons.filled` | 2.36 MB |
| **整个 App 的 DEX 合计** | **27.27 MB** |

**一半以上的 DEX 是它。** 删掉之后：

| | 删前 | 删后 | 变化 |
|---|---|---|---|
| APK 文件 | 20.01 MB | **12.41 MB** | **-7.60 MB（-38%）** |
| DEX 未压缩合计 | 27.27 MB | 13.33 MB | -13.94 MB（-51%） |
| DEX 压缩后 | 18.96 MB | 12.06 MB | -6.90 MB |

`material3` 自身带的 `material-icons-core` 仍然保留，基础图标不受影响。

---

## 4. 另一个容易误判的坑：增量构建会在 APK 里留垃圾

第一次删掉依赖后重新 `assembleDebug`，**APK 大小几乎没变**（20,013,962 → 20,013,792 字节，
只差 170 字节）——看起来像"删了没用"。

实测原因是 **AGP 增量构建复用了上一次的 APK 文件，把新内容写进去、却没有回收旧数据**：

| | APK 文件 | zip 内容压缩合计 | 差值 |
|---|---|---|---|
| 增量构建后 | 20.01 MB | 12.94 MB | **7.06 MB 是孤儿数据** |

逐条目核对可以定位到具体空洞：`lib/arm64-v8a/libandroidx.graphics.path.so` 之后
有 **6.25 MB** 的空隙——那是上一版 dex 的残留，中央目录已不再引用它。

**结论：只有 `clean` 之后重建，体积数据才可信。** 这也解释了为什么"改了代码但包大小没动"
经常是个假象。

---

## 5. 那 daemon 那 17,771 行 Go 去了哪

`daemon/pocketagentd.exe` = **19.5 MB**，跑在用户的 Windows 电脑上，通过
gRPC（端口 7246）被手机连接。

它和 APK 的关系只有一条：**proto 契约**。7 个 `.proto` 文件在两个仓库位置各存一份
（`proto/v1/*` 与 `android/app/src/main/proto/v1/*`，MD5 必须一致），
手机侧只把生成的桩类打进去 —— 467 KB，占 APK 的 3.5%。

所以本轮 daemon 侧的改动（反向请求分派、goal 下发）**不会也不应该**影响 APK 体积：
它们是电脑上那个 exe 重新编译，手机端只多认了几个 `ToolCallBlock.name` 字符串常量。

---

## 6. 想进一步减体积，看这几处

按收益排序（都已实测，不是猜测）：

| # | 手段 | 预估收益 | 代价 |
|---|---|---|---|
| 1 | ✅ 已做：删掉 `material-icons-extended` | **-7.6 MB** | 无 |
| 2 | 开 `minifyEnabled` + R8（release 构建） | 通常 -30%~50% DEX | 需要配 keep 规则；debug 包不适用 |
| 3 | 用 `debug` 的 `isMinifyEnabled=false` 但 release 开 shrinkResources | 再 -0.5 MB | 低 |
| 4 | Guava 1.76 MB：多是 gRPC 传递依赖，可用 `grpc-protobuf-lite`（已在用）+ 排除 guava 的 android 变体 | 待评估 | 有兼容风险 |
| 5 | ABI 拆分（只发 arm64） | `lib/` 才 0.04 MB，**收益为 0** | 不值得 |

注意第 5 条：`lib/` 只有 0.04 MB，所以"分 ABI 包"在这个项目上毫无意义 ——
这与常见 APK 精简经验（原生库占大头）正好相反，因为本项目**几乎没有原生库**。

---

## 7. 给用户的一句话回答

> 改动的大头在**电脑上的 daemon**（17,771 行 Go，编译成 19.5 MB 的 `pocketagentd.exe`），
> 它不进 APK。手机侧的 Kotlin 全加起来只有 1.13 MB DEX，占 APK 的 8.5%——
> 所以修多少 bug 都不会让包明显变大或变小。
>
> 反过来，顺手查出一个**零引用**的依赖 `material-icons-extended`，
> 它一个人占了 DEX 的一半以上。删掉后 APK 从 **20.0 MB 降到 12.41 MB（-38%）**。
> 而且第一次删完看着"没变小"，是因为 AGP 增量构建在包里留了 7 MB 孤儿数据 ——
> 必须 clean 重建才测得准。
