## 一、缓存机制

### 1.1 现状梳理

**做得好的（保持）：**
- **单一真相设计**：TaskCenter 不缓存轮次副本，只持 `threadId` 引用实时读 `TurnSession`，不存在"任务中心完成、聊天页还在转"的双份状态（TaskCenter.kt 头注）。
- **临时文件自清理**：zip 列表与 PDF 渲染的 cacheDir 临时文件均在 `finally` 中删除（PcFilePreview.kt:638/1135/1174）。
- **显式 maxBytes**：预览 64MB、下载 512MB 均显式给上限，规避 daemon 默认 2MB 静默截断（BrowserScreen.kt:544、PaDownloader.kt:29）。
- **用量本地缓存**：ThreadUsageStore 解决"重开会话上下文窗口从 0% 开始"，纯客户端、兼容老 daemon。
- **下载进度单调不减**、MediaStore 免权限写入、MIME 统一走 FileKind。

**问题清单：**

#### C1 TaskCenter 高频全量持久化（IO/CPU 放大）【性能 · 高】
- **现状**：`updateDownload` 在**每个 64KB 分块**到达时调用 `persist()`（TaskCenter.kt:136-143 → 190-212）。persist 会：重新发射整个任务列表 StateFlow、重算未读数、把全部任务拼成一个大字符串全量重写 SharedPreferences。
- **潜在影响**：下载 512MB 文件 = 8192 次全量字符串重写 + 全列表拷贝 + StateFlow 重发射。下载大文件时可感知卡顿与无谓 IO；任务清单越大（D3）放大越明显。
- **建议方案**：把"磁盘写"与"UI 通知"分离——UI 仍每块刷新，但 persist 节流（如 300ms 合并 / 每变化 1% 写一次 / 完成与失败必写）。进一步可把任务清单迁到 DataStore（protobuf/文件级原子写），或在下载进行中只写内存、落盘降频。

#### C2 PC 文件预览零内容缓存【效率 · 高】
- **现状**：每次预览都走 gRPC `readFile` 全量拉取（上限 64MB）→ 解析 → 拼 HTML → `loadDataWithBaseURL`。无任何磁盘/内存 LRU。同一文件看第二次仍是完整传输+完整渲染。
- **潜在影响**：重复预览浪费带宽与时间（USB 下尚可，Tailscale 中继下明显）；预览结果不可复用，直接导致离线三-2 的"刚看过的文件断线后打不开"。
- **建议方案**：在 cacheDir 建内容缓存（键 = `path + size + mtime` 哈希，LRU 上限如 200MB，超限淘汰最旧）。命中则跳过 gRPC 直接渲染；同时天然成为离线"最近预览过"的能力（见三-3）。

#### C3 会话数据零本地缓存【离线体验 · 高】
- **现状**：会话列表 `listThreads`（ThreadsScreen.kt:171）、会话详情 `getThread`、历史 `getThreadHistory`（ChatScreen.kt:1186-1210）全部直连 daemon，无本地快照。失败即白屏报错："无法加载会话历史：连接失败"。
- **潜在影响**：断网/拔线时打开 app，会话列表空、聊天页报错——手机上没有任何"上次的会话长什么样"的痕迹；对一个"遥控器"形态的 app，这是离线体验的最大空洞。
- **建议方案**：低成本先行——每次 `listThreads` 成功后把 (id, title, updatedAt) 快照写入本地（JSON 文件或 DataStore），断线时渲染快照并标记"离线快照 · 点击重试"；聊天历史同理缓存最近 N 条（每会话上限如 200KB，总量 LRU）。只读、不加写入口，实现面小、收益大。

#### C4 SharedPreferences 键随会话无限增长【卫生 · 中】
- **现状**：`threadModel:<threadId>`（AgentConnection.kt:310-320）与 `pa_thread_usage` 的每会话键都没有删除路径；会话在电脑端删除后，手机端键永久残留。
- **潜在影响**：单键量小，但无上界；SP 是全量 XML 加载，长期积累拖慢冷启动读取，且与"本地会话清理"语义脱节。
- **建议方案**：统一加回收——listThreads 刷新时对比快照，把"电脑端已不存在的会话"对应的 threadModel / usage 键延迟清理（如 7 天后清，防误删）；或提供"清空会话本地数据"入口。

#### C5 WebView 存储从未清理【卫生 · 中】
- **现状**：`javaScriptEnabled=true`、`domStorageEnabled=true`（BrowserScreen.kt:408-409），HTTP 缓存走默认 LOAD_DEFAULT；从未调用 WebStorage/缓存清理 API，也没有清理入口。内置浏览器有两类流量：本地渲染 HTML（无网络，无缓存问题）与「网页」入口的真实站点（会产生 HTTP 缓存 + localStorage）。
- **潜在影响**：长期使用后 `app_webview` 与 HTTP 缓存持续增长；用户无感知也无手段回收。
- **建议方案**：在"缓存管理"（见二-4）里加"清理浏览器数据"：`WebStorage.deleteAllData()` + 删除 WebView HTTP 缓存目录 + `clearFormData()`。浏览功能本身保留缓存（对体验有益），只做用户主动/定期清理。

#### C6 `allowBackup=false` 的取舍【备份 · 低】
- **现状**：Manifest 关闭了系统备份（安全取向正确：token/会话元数据不进云备份）。
- **潜在影响**：换机/重装时全部本地偏好（含下载任务索引）不迁移。下载文件本体在公共 Download 目录不受影响，但任务条目、置顶、用量缓存全丢。
- **建议方案**：保持 false（token 在 prefs 里明文存储，进备份反而是风险）。可接受现状；若未来做迁移，用自有的导出/导入而不是打开 allowBackup。

## 二、缓存清理

### 2.1 现状：已有能力
| 入口 | 动作 | 实际效果 |
|---|---|---|
| 任务中心底部「清理已完成的任务」 | `TaskCenter.clearFinished()` | **只删任务条目**，不触碰文件本体 |
| 设置 → 用户数据管理 → 单条「删除」 | `deleteLocalFile()` + `TaskCenter.remove()` | 删 MediaStore 文件 + 条目，二者同步（这是唯一既删文件又删条目的地方）|
| 连接卡「清空输入」 | 重置地址/token 表单 | 与缓存无关 |

除此之外**没有任何缓存清理能力**：无 WebView 清理、无预览缓存（因为还没有内容缓存）、无失效键回收、无启动清扫。

### 2.2 问题清单

#### D1 下载失败残留半截文件【正确性 · 高，建议优先修】
- **现状**：`PaDownloader.downloadFromPc` 先 `createSink()`（MediaStore 已 insert 出真实条目），随后流式写入；`catch` 分支只调 `finishDownload(false)`，**不删除已 insert 的 uri**（PaDownloader.kt:83-88）。`saveTextAsFile` 同构。
- **潜在影响**：每次失败下载都在系统"下载/PocketAgent"里留下 0KB 或半截文件；用户在 app 里看不到（无条目可点开成"失败"），只能在系统文件管理里手工翻找。反复重试反复残留。
- **建议方案**：catch（及"下载到一半但 totalSize 校验失败"）时 `ctx.contentResolver.delete(target.third, null, null)` 把半成品删掉再报失败；低版本路径同样删 `File`。

#### D2 系统侧删除不感知（悬空条目）【正确性 · 中】
- **现状**：`localUri` 落在 task_center prefs；用户在系统文件管理/清理软件里删了文件后，app 条目仍在，点「查看」走 `openLocalFile` → content URI 已失效，行为未定义（大概率静默失败或空白）。
- **潜在影响**：用户以为文件还在；"查看"偶发失灵显得 app 不稳定。
- **建议方案**：打开前做存在性校验（`contentResolver.openFileDescriptor(uri, "r")` try-catch 或 query size），失效则提示"文件已被移动或删除"，并提供"从列表移除该条目"的一键操作。

#### D3 任务清单无上限【卫生 · 中】
- **现状**：任务条目只增不减（除非手动清理），persist 把全部条目拼成一个字符串重写；restore 时全量解析。
- **潜在影响**：重度使用数月后字符串变大，叠加 C1 的每块重写，写入成本线性上升。
- **建议方案**：persist 时裁剪——非 RUNNING 且已读的任务按"每类保留最近 N 条（如 50）+ 最旧优先淘汰"；淘汰前如 localUri 仍有效可选提示。这样也顺带压住 C1 的放大系数。

#### D4 cacheDir 崩溃残留无清扫【卫生 · 低】
- **现状**：临时文件靠 `finally` 自删；进程被杀/崩溃时残留（`pa_pdf_*`、`pa_ziplist*`），无启动清扫。
- **潜在影响**：单文件最大 64MB（PDF 预览字节落盘），崩溃后残留可能占可观空间；系统存储紧张时会清 cacheDir，但平时无主动回收。
- **建议方案**：MainActivity 启动时清扫 cacheDir 下匹配 `pa_pdf_*` / `pa_ziplist*` 的文件（只删已知前缀，避免误伤 WebView 等共享目录内容），零成本。

#### D5 失效偏好键无回收
- 见 C4（threadModel、usage 键）。

### 2.3 应清理 / 应保留矩阵（策略基线）

| 类别 | 处置 | 理由 |
|---|---|---|
| 下载失败的半截文件 | **自动清**（写失败即删） | 无价值、误导用户 |
| 崩溃残留的 cacheDir 临时文件 | **启动时自动清**（按前缀） | 纯临时产物 |
| 预览内容缓存（未来 C2） | **LRU 自动清**（上限 200MB，最旧先淘汰） | 可再生数据 |
| WebView 缓存/DOM Storage | **用户手动清**（设置入口）+ 不做后台自动 | 保留浏览体验 |
| 非运行中的陈旧任务条目 | **数量上限滚动清**（每类保留最近 ~50） | 索引会无限增长 |
| 失效会话的偏好键（threadModel/usage） | **延迟自动清**（确认会话已删 7 天后） | 防误删 |
| 用户设置（连接/外观/字号/置顶） | **永不自动清** | 用户资产 |
| 已下载文件本体 | **只随用户显式删除**（用户数据管理） | 用户内容，清理不可逆 |
| 会话离线快照（未来 C3） | **LRU 限额自动清** | 可再生，但删了离线体验就没了 |

### 2.4 建议新增：设置页「缓存管理」二级页
- **现状**：无处可看"app 到底占了多少本地空间"，也没有一键清理。
- **潜在影响**：用户遇到"手机空间不足"时对 app 无抓手，只能卸载重装（连 token 一起丢）。
- **建议方案**：在用户数据管理下加一节"缓存"，展示各分区占用（下载文件总量按 MediaStore 查询、cacheDir 现用量、WebView 数据量、任务条目数），提供三个动作：清理临时与失效缓存（前缀清扫 + 悬空条目 + 失效键）、清理浏览器数据（C5）、清空任务条目（保留文件本体，需二次确认）。

## 三、离线可用性

### 3.1 连接层现状（这一层做得扎实）
- 多候选回退：`lastGoodAddr → USB(1.5s 超时) → 局域网 → Tailscale(6s) → 手填`（AgentConnection.kt:216-265）；
- 自动重连：断线后 1→2→5→10s 指数退避 + 网络事件即时唤醒（NetworkCallback），恢复后 `connectionEpoch+1` 驱动全局刷新（AgentConnection.kt:501-549）；
- 冷启动回显：`lastGoodAddr` 快照让探活完成前就显示"上次连接"的通道与地址。
- **结论：断线检测与恢复已经是产品级，问题不在"发现断线"，而在"断线后还剩什么能用"。**

### 3.2 功能离线矩阵（实测代码路径推演）

| 功能 | 断线时 | 依据 |
|---|---|---|
| 查看已下载文件（内置浏览器/系统打开） | ✅ 可用 | 本地 MediaStore，不碰网络 |
| 分享/删除已下载文件 | ✅ 可用 | 同上 |
| 任务中心列表与角标 | ✅ 可用 | SP `task_center` |
| 设置、外观、置顶、用量回显 | ✅ 可用 | 本地 prefs（用量是缓存快照） |
| 会话列表 | ❌ 空白 | `listThreads` 直接 gRPC，无快照 |
| 打开会话/聊天历史 | ❌ 报错"无法加载会话历史" | `getThread/getThreadHistory` 无本地缓存（ChatScreen.kt:1190/1209）|
| 发消息/审批/中断 | ❌ 不可用 | 依赖 daemon 流式通道 |
| 终端 / PC 文件浏览 / Git | ❌ 不可用 | 全部 gRPC 实时（FilesScreen.kt:112-160 等）|
| PC 文件预览 | ❌ 不可用（**包括刚看过的文件**） | 零内容缓存（C2）|
| 下载新文件 | ❌ 失败（任务条目留在"失败"） | readFile 依赖 daemon |

### 3.3 缺失能力与改进方向（按投入产出排序）

#### O1 会话列表/标题离线快照【建议做，成本低】
- **现状**：见 C3。
- **建议**：listThreads 成功后写只读快照；断线时列表照常展示（标"离线快照"），点击进会话用历史快照（O2）或提示需连接。快照同时服务 C4 的失效键回收。

#### O2 最近会话内容只读快照【建议做，成本中】
- **现状**：聊天历史全量依赖 daemon。
- **建议**：`getThreadHistory` 成功后按会话缓存"最近 N 条渲染好的消息（上限每会话 200KB、总量 LRU）"；断线进入会话时渲染快照 + 顶部横幅"离线，显示的是 X 日前的记录"，输入框置灰但保留"排队发送"可选（O4）。

#### O3 预览结果离线可用【建议做，成本中】
- **现状**：刚预览过的 XLSX/PDF 断线后立刻打不开。
- **建议**：与 C2 的内容缓存是同一件事——缓存原始字节（按 mtime 失效），离线命中即渲染；这也是"预览缓存"最主要的用户价值。

#### O4 下载断点/重试体验
- **现状**：失败重试从 0 开始整段重传（gRPC 流无续传）；失败任务有「重试」入口（消息类会先 resync 再进会话，这个设计好）。
- **建议**：短期保持重试语义、配合 D1 清理半截文件即可；中期可让下载先落 cacheDir 分块文件、全部完成后再原子搬进 MediaStore，顺带获得"失败不产生系统垃圾"与未来续传的基础。

#### O5 断线状态的主动告知
- **现状**：连接卡与"未连接 · 自动重连中"已有；但文件/终端页失败时只吐一次性错误文本。
- **建议**：各 gRPC 依赖页统一消费 `connState`，down 时整页置灰 + 常驻顶条"已与电脑断开，正在自动重连…"，替代分散的报错文案，与既有设计语言一致。

## 四、其他优化点

### 4.1 性能与内存
| # | 问题 | 现状 | 潜在影响 | 建议 |
|---|---|---|---|---|
| P1 | 预览内存峰值 | readFile 全量 ByteArray（≤64MB）+ 拼 HTML 字符串（base64 内联页图）+ `loadDataWithBaseURL` 再拷贝 | 最坏情况数倍于原文件的内存峰值，低端机有 OOM 风险；现状已有 MAX_ROWS=800/MAX_COLS=40/MAX_PDF_PAGES=12/MAX_SLIDES=40 缓解 | 已有的上限策略保持；对 >16MB 的文档类文件改为"提示下载后打开"或分块渲染；C2 缓存可复用同一份字节避免重复持有 |
| P2 | TaskCenter 写放大 | 见 C1 | 下载大文件时 IO/CPU 浪费 | 见 C1 |
| P3 | PDF 页图质量/体积 | 1000px 宽 JPEG 78% | 单页约 200-400KB、12 页可控 | 可保持；若未来提页数上限，改为页图落 cacheDir + `<img src="file://">`，避免 HTML 字符串膨胀 |
| P4 | daemon 分块粒度 | readFile 64KB/块，512MB 下载 = 8192 个消息 | USB 下无感，Tailscale 中继下有协议开销 | daemon 侧对大文件协商增大分块（256KB-1MB）；app 侧 maxInboundMessageSize 16MB 充裕，无需动 |

### 4.2 稳定性与安全
| # | 问题 | 现状 | 潜在影响 | 建议 |
|---|---|---|---|---|
| S1 | 半截文件残留 | 见 D1 | 用户可见的系统垃圾 | **P0 修**：失败路径删 uri |
| S2 | 删除静默失败 | `deleteLocalFile` runCatching 吞异常，之后必 toast"已删除"（SettingsScreen.kt:1025-1028、1563-1572） | 删除失败时用户被误导 | 按 delete 返回/异常给差异化提示 |
| S3 | token 明文存储 | SP `agent_conn` 明文；gRPC `usePlaintext()`（代码已自注 P0/P1 计划） | root/物理接触场景可读；链路可被同网窃听 | 中期：EncryptedSharedPreferences + 自签 TLS（局域网/Tailscale 均适用）；USB 通道风险低可后置 |
| S4 | getThreadHistory 全量返回 | 一次拉整段历史 | 超长会话首开慢、内存峰值 | daemon 侧加分页（按序号/时间倒推 N 条），配合 O2 快照 |
| S5 | `usesCleartextTraffic=true` | 全局允许明文 | 与 S3 同源；不影响功能 | 收敛为 networkSecurityConfig：仅放行 daemon 地址族 |

### 4.3 代码结构
| # | 问题 | 现状 | 建议 |
|---|---|---|---|
| R1 | 巨石文件 | ChatScreen.kt 116KB、SettingsScreen.kt 69KB、PcFilePreview.kt 67KB、ThreadsScreen.kt 50KB、GitScreen.kt 38KB | 按既有 component 惯例拆：ChatScreen → 消息列表/输入区/审批卡/导出；SettingsScreen → 各二级页一文件；PcFilePreview → 每格式一 renderer（`render(ctx, kind, bytes, pal)` 分发）|
| R2 | 全局单例承载状态 | AgentConnection 单例同时管连接、全部偏好、模型策略 | 可接受（规模尚可控）；若继续膨胀，把"偏好存取"收拢成 PreferencesStore，连接逻辑独立 |
| R3 | 偏好存储分散 | 4 个 SP 文件 + 各自 init() | 统一到 DataStore 是理想态；成本高、收益主要是 C4/D3 类卫生问题，可与"缓存管理"一起排期 |

### 4.4 值得保持的设计（避免后续重构误伤）
- 下载走自实现 gRPC 流而非 DownloadManager（输入不是 URL，代码注释已论证）；
- MediaStore + FileProvider 兜底 file:// 的分享路径；
- 连接回退链与 `manualAddress`/`address` 分字段（防手填值被候选覆盖，踩过坑的修复）;
- 预览页全主题化（Pal/pal()）与 `guard(pal)` 失败页统一；
- TurnSession 中断任务的 resyncFromDaemon 重试语义。

## 五、优先级路线图（结论）

| 优先级 | 事项 | 对应问题 |
|---|---|---|
| **P0（正确性，先修）** | 下载失败清理半截文件；悬空下载条目的存在性校验与提示；删除失败不再谎报"已删除" | D1 / D2 / S2 |
| **P1（体验增益最大）** | TaskCenter persist 节流；预览内容磁盘缓存（= 离线预览）；会话列表/最近消息离线快照；启动清扫 cacheDir 前缀；设置页「缓存管理」 | C1 / C2+O3 / C3+O1+O2 / D4 / 二-4 |
| **P2（结构与长期）** | 任务清单滚动上限；失效偏好键回收；浏览器数据清理入口；token 加密存储 + TLS；ChatScreen/SettingsScreen/PcFilePreview 拆分；daemon 历史分页与大文件分块增大 | D3 / C4 / C5 / S3-S5 / R1 / P4+S4 |

**一句话总结**：连接层（断线检测/多候选回退/自动重连）已是产品级；真正的短板集中在三处——**没有内容缓存**（预览与会话数据断线即失明）、**失败路径不回收**（半截文件/悬空条目/无限增长的任务清单与偏好键）、**持久化写放大**（下载分块触发全量重写）。先修 P0 三个正确性问题，再补"内容缓存 + 离线快照"这对组合拳，离线体验即可从"只剩本地文件"跃升到"列表可看、最近会话可读、刚看过的文件可开"。
